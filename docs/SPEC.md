## 1. תקציר

Slidr הוא עורך מצגות שולחני (Tauri) שבו ה-AI הוא שותף מלא לעריכה ולא תוסף. המסך מחולק לשניים:

- **שני שלישים — העורך:** כלי עריכה למעלה, השקף במרכז, רצף השקפים למטה. עורך מלא ברמת PowerPoint/Canva: טקסט, תמונות, צורות, טבלאות, גרפים, מדיה, תבניות, מעברים ואנימציות.
- **שליש — אזור ה-AI והכלים:** toolbar אנכי ופאנל. שלושה כלי AI לפי היקף: **מצגת**, **שקף**, **אובייקט**. בכל אחד צ'אט ופעולות מוכנות.

בממשק עברי אזור ה-AI בימין והעורך בשמאל; בממשק אנגלי הפריסה משתקפת.

ה-AI פועל דרך Agent Harness חיצוני (בגרסה הראשונה Claude Code CLI) שמקבל גישה למצגת דרך ה-Deck API שהאפליקציה מגדירה. אותו API בדיוק משמש כל harness עתידי.

### 1.2 מחוץ להיקף (Non-goals)

- תאימות לקובצי PowerPoint (‎.pptx) — לא ייבוא ולא ייצוא.
- ענן, חשבונות משתמש, שיתוף ועריכה משותפת בזמן אמת.
- גרסת web או מובייל.
- installer חתום, auto-update, רישוי וטלמטריה (כלי אישי / צוות קטן).
- שחזור המודל מ-HTML: ייבוא הוא תמיד המרה מחדש, גם לקובץ ש-Slidr ייצא. המראה נשמר במלואו (5.9); מה שלא חוזר הוא מידע שקיים רק במודל, כמו מזהים, שמות אובייקטים והיסטוריית שיחות.

## 4. פריסת מסך ו-UX

### 4.0 שפת העיצוב של האפליקציה

האפליקציה עצמה היא מוצר מעוצב. הרף הוא Figma, Canva ו-Linear: ממשק שקט, מדויק ומהיר, שבו השקף הוא הכוכב והכלים נסוגים לרקע. זו דרישה מחייבת מהיום הראשון, לא שלב ליטוש בסוף.

**עקרונות**

1. **התוכן במרכז.** משטחי הממשק ניטרליים ושקטים; הצבע היחיד שבולט הוא צבע ההדגשה, והוא שמור לפעולה הראשית ולמצבי AI.
2. **צפיפות מדויקת.** כלים קומפקטיים בלי עומס: grid של 4px, גובה פקד 32px, אייקונים של 16–18px, קבוצות מופרדות ברווח ולא בקווים.
3. **עומק עדין.** שכבות מובחנות בגוון משטח ובצל רך אחד, רדיוס עקבי (8px לפקדים, 12px לפאנלים וכרטיסים). בלי מסגרות כבדות ובלי gradients בממשק.
4. **טיפוגרפיה נקייה.** Inter ללטינית ו-Heebo לעברית, סולם של 12 / 13 / 14 / 16 / 20. היררכיה במשקל ובצבע, לא בגודל.
5. **תנועה שמסבירה.** מעברים של 120–200ms לפתיחת פאנלים, ריחוף ובחירה. שום דבר לא קופץ ושום דבר לא מתעכב.
6. **ה-AI מורגש.** הזרמת טקסט חלקה, שבבי פעולה שמתעדכנים חי, הילה עדינה על אובייקט שה-Agent נוגע בו, ושלדים (skeletons) במקום ספינרים.
7. **אין פקדי ברירת מחדל של המערכת.** כל פקד (תפריט, גלילה, בורר צבע, tooltip, דיאלוג) מעוצב במערכת העיצוב של האפליקציה.

### 4.1 יעד רזולוציה

הפריסה מתוכננת ל-**1920×1080 בחלון ממוקסם** (שטח נטו 1920×1032 אחרי שורת המשימות של Windows) ב-100% scaling. רזולוציית מינימום נתמכת: 1366×768, שבה הפאנל מתכווץ ל-420px והשקף מוצג בקנה מידה קטן יותר.

## 5. מודל המסמך

### 5.1 עקרונות

1. **מודל אובייקטים במיקום מוחלט.** כל אובייקט הוא מלבן (`frame`) במרחב 1920×1080 עם סיבוב. זה מה שמאפשר חיתוך, סיבוב, שכבות, אנימציות ו-undo אמינים.
2. **יחידות:** פיקסלים לוגיים במרחב השקף. גודל גופן 32 פירושו 32px בשקף 1920×1080.
3. **קישור ל-Theme דרך tokens.** ערך יכול להיות token (`{ token: "primary" }`) או ערך מפורש. החלפת תבנית משנה את כל מה שמקושר.
4. **סכמה אחת כמקור אמת.** סכמות Zod מגדירות את המודל; מהן נגזרים טיפוסי TypeScript ו-JSON Schema לכלי ה-Agent.
5. **כל שינוי עובר דרך Command.** אין כתיבה ישירה ל-store. ראה פרק 6.
6. **גרסאות סכמה והגירות.** `schemaVersion` + פונקציות migration בטעינה.
7. **המודל לא מגביל את ה-HTML.** כל אובייקט נושא שדה `css` למאפיינים שהמודל לא מכיר, ואובייקט מסוג `html` מחזיק כל HTML/CSS/JS כמו שהוא. ראה 5.9.

### 5.3 סוגי אובייקטים

| סוג | שדות עיקריים | הערות |
|---|---|---|
| `text` | `content: RichText`, `autoFit` (none / shrink / growHeight), `vAlign`, `padding`, `columns`, `wrap` | ראה 5.4. `wrap: false` משאיר כל פסקה בשורה אחת (טקסט מיובא, ADR-005) |
| `image` | `assetId?`, `prompt?`, `crop` (מלבן מנורמל 0..1), `fit` (cover/contain/fill), `mask`, `adjust` (brightness, contrast, saturation, temperature, blur, grayscale, hue), `filterPreset`, `border`, `alt` | לא הרסני: הנכס המקורי נשמר תמיד. בלי `assetId` זה placeholder שמחכה לתמונה לפי `prompt` (11.5) |
| `shape` | `geometry` (preset או path), `fill`, `stroke`, `content?: RichText` | כ-40 צורות מוכנות |
| `line` | `points`, `stroke`, `startHead`, `endHead`, `curve` | קו, חץ, עקומה |
| `svg` | `assetId` או `markup`, `colorOverrides` | אייקונים ואיורים וקטוריים; צביעה מחדש לפי tokens |
| `group` | `children: Element[]` | קואורדינטות הילדים יחסיות לקבוצה |
| `table` | `rows`, `cols`, `cells` (RichText, span, fill, borders), `style` (header, banded) | |
| `chart` | `chartType`, `data` (categories, series), `options` (legend, axes, labels, palette) | bar, column, line, area, pie, donut, scatter, radar |
| `video` | `assetId`, `poster`, `autoplay`, `loop`, `muted`, `trim`, `volume` | |
| `audio` | `assetId`, `autoplay`, `loop`, `trim`, `volume`, `showControls` | |
| `html` | `markup`, `styles`, `hasScripts`, `natural` | כל HTML/CSS/JS כמו שהוא. אובייקט מן המניין: זז, משנה גודל, מסתובב, מונפש ונערך (8.9). `styles` הוא ה-stylesheet של התוכן (השדה `css` שבבסיס מעצב את התיבה); `natural` הוא הגודל שבו התוכן נפרס, והוא מוקטן למסגרת ולא נפרס מחדש (ADR-005) |

טיפוסי עזר: `Fill` = solid / linear / radial / conic gradient / image / none / css (כל ערך CSS שאין לו צורה במודל, כמו שהוא). `Background` = `Fill` + שכבת overlay + טשטוש והכהיה לתמונת רקע. `Color` = token או ערך מפורש עם alpha.

הסכמות עצמן (Zod) נמצאות ב-`packages/model/src/schema/`, והן מקור האמת; ADR-007 מתעד את ההבדלים מהטבלה הזו.

### 5.7 נכסים (Assets)

- אחסון לפי תוכן: שם הקובץ הוא ה-sha256 שלו. אותו קובץ לא נשמר פעמיים.
- `AssetMeta`: mime, מידות, גודל, מקור (upload / stock / ai / import), ייחוס ורישיון (לסטוק), ושושלת (`parentAssetId`, prompt, ספק) לתמונות AI.
- נכס שאין אליו הפניה נמחק רק בשמירה, לא מיד — כדי ש-undo יעבוד. "הפניה" היא כל מופע של מזהה הנכס במצגת, גם בתוך markup של אובייקט `html` או בשדה `css`. גופנים משמשים לפי שם משפחה ולכן לא נמחקים בשמירה (ADR-007).
- **גופנים הם נכסים.** גופן שהגיע עם קובץ מיובא (WOFF2 מוטמע) או שהמשתמש הוסיף נשמר בקובץ המצגת, נטען ב-renderer כמו גופן מובנה, ומוטמע בייצוא. כך מצגת מיובאת נראית זהה גם במחשב שהגופן לא מותקן בו.

### 5.9 עקרון הנאמנות: המודל עוזר, לא מגביל

המודל קיים כדי לאפשר עריכה נוחה (ידיות, חיתוך, שכבות, undo). הוא לא רשימת היכולות של המצגת. כל מה שאפשר לכתוב ב-HTML/CSS אפשר להציג ב-Slidr, גם אם אין לו שדה במודל. שלושה מנגנונים מבטיחים את זה:

| מנגנון | מה הוא מכסה | דוגמה |
|---|---|---|
| שדה `css` בכל אובייקט | מאפיין CSS של אלמנט בודד שאין לו שדה במודל | `clip-path`, `mix-blend-mode`, `backdrop-filter`, `text-shadow` |
| שדה `css` בשקף | הגדרות ברמת stylesheet | `@keyframes`, `@font-face` |
| אובייקט `html` | תת-עץ שלם שהמשמעות שלו תלויה במבנה ה-DOM או ב-JS | canvas מונפש, גרף של ספרייה חיצונית, pseudo-elements מורכבים, טקסט שזורם סביב צורה |

**כלל ההמרה:** נאמנות לפני עריכוּת. ההמרה לאובייקטים היא שיפור שמופעל רק כשהוא לא משנה את המראה. אחרי המרת כל שקף משווים אותו למקור; אזור שנראה אחרת חוזר להיות אובייקט `html`. במקרה הקיצון שקף שלם הוא אובייקט `html` אחד — וגם אז הוא מוצג, מיוצא ומוצג במצגת כרגיל.

**מה אפשר לעשות עם אובייקט `html`:** ראה 8.9. בקצרה: הכול חוץ מידיות עריכה ייעודיות לתוכן הפנימי, ואפשר "לפרק לאובייקטים" לפי בקשה.

## 9. תבניות, הנחיות עיצוב ובדיקת עיצוב

זה הפרק שמממש את D13. הדרישה: **כל שקף שה-Agent יוצר מעוצב, נראה טוב, ומנצל את שטח השקף באופן מיטבי.** "כותרת ותבליטים על רקע ריק" אינו תוצר קביל.

ארבעה מנגנונים פועלים יחד: **הנחיות** שה-AI מקבל (9.1), **lint** שמודד בפועל (9.2), **layouts** ותבניות שמיישמים את ההנחיות מראש (9.3), ו-**שער איכות** שלא נותן ל-Agent לסיים תור עם שקף לקוי (9.4).

### 9.1 הנחיות העיצוב (מודול קבוע ב-system prompt של כל harness)

**משטח ו-grid**

- משטח 1920×1080. שולי בטיחות: 96px בצדדים, 80px למעלה ולמטה. אזור התוכן: 1728×920.
- grid של 12 עמודות, מרווח 24px. יחידת ריווח בסיסית 8px; כל מרווח הוא כפולה שלה.
- רקעים, תמונות ואלמנטים דקורטיביים רשאים ומעודדים לחרוג מהשוליים עד קצה השקף (full-bleed). טקסט לא.

**ניצול השטח**

- התוכן ממלא את אזור התוכן. מלבן החוסם של כל האובייקטים המשמעותיים מכסה לפחות 70% מאזור התוכן.
- אין "אזור מת": רבע שקף ריק בלי כוונה עיצובית הוא ליקוי. רווח לבן הוא החלטה, לא שארית.
- התוכן מאוזן: מרכז הכובד החזותי קרוב למרכז השקף, אלא אם ה-layout אסימטרי בכוונה ומאוזן באלמנט נגדי.
- תמונות ממלאות את המסגרת שלהן (cover) ואינן מוצגות קטנות באמצע שטח ריק.

**טיפוגרפיה (פיקסלים ב-1920×1080)**

| סגנון | גודל | שימוש |
|---|---|---|
| display | 120–160 | שקף פתיחה, מספר גדול |
| title | 72–96 | כותרת שקף |
| heading | 44–64 | כותרת משנה, כותרת כרטיס |
| body | 28–36 | גוף הטקסט |
| caption | 20–24 | הערות, מקורות, תוויות |

- מינימום מוחלט לטקסט קריא: 24px. לכל היותר שתי משפחות גופנים במצגת.
- רעיון אחד לשקף. עד כ-40 מילים ועד 5 תבליטים; טקסט ארוך מפוצל לשני שקפים או הופך לוויזואליה.
- היררכיה ברורה: יחס גודל של 1.5 לפחות בין רמה לרמה, ונקודת מיקוד אחת לשקף.

**שפה חזותית מודרנית**

- כותרות גדולות ונועזות; תמונות גדולות, רצוי full-bleed עם שכבת הכהיה לקריאות.
- משמעת צבע 60/30/10: רקע / משטחים / הדגשה. צבע הדגשה אחד, בשימוש מדוד.
- עומק: כרטיסים עם רדיוס עקבי וצל רך, gradients עדינים, צורות דקורטיביות בשקיפות נמוכה.
- סגנון אייקונים ותמונות אחיד לכל המצגת (`meta.imageStyle`).
- גיוון: לא יותר משני שקפים רצופים באותו archetype.

**ארכיטיפים של שקפים**

hero / פתיחה · מפריד מקטע · מספר גדול / סטטיסטיקה · ציטוט · טקסט + תמונה (שתי עמודות) · תמונה מלאה עם טקסט · רשת כרטיסים (3 / 4 / 6) · ציר זמן · שלבי תהליך · השוואה · גרף במוקד · טבלה · צוות · סיום / קריאה לפעולה.

**RTL**

- במצגת עברית ה-layout משתקף: טקסט בימין, תמונה בשמאל; ציר זמן ותהליך מימין לשמאל.
- יישור `start`, לא `right`. מספרים ומונחים לטיניים בתוך טקסט עברי נשארים LTR.
- זיווג גופנים: גופן עברי וגופן לטיני תואם במשקל ובגובה.

**תנועה**

- אנימציה משרתת סדר קריאה, לא קישוט. משך 300–600ms, easing אחיד.
- סוג מעבר אחד למצגת (או אחד לכל מקטע). כניסה מדורגת (stagger) לרשימות ולכרטיסים.

**נגישות**

- ניגודיות לפי WCAG AA: 4.5:1 לטקסט רגיל, 3:1 לטקסט גדול (מעל 48px).

### 9.4 שער האיכות העיצובי של ה-Agent

ההנחיות לבדן לא מספיקות: מודל יכול לקרוא אותן ועדיין להפיק שקף חלש. לכן האפליקציה אוכפת תהליך עבודה, ולא רק מבקשת אותו.

**תהליך העבודה המחייב (מוגדר ב-prompt של כל harness)**

1. **תכנון לפני בנייה.** לכל שקף ה-Agent בוחר ארכיטיפ ומחליט מהו האלמנט החזותי המרכזי (תמונה, מספר גדול, גרף, דיאגרמה, רשת כרטיסים). שקף בלי אלמנט חזותי מותר רק בארכיטיפים טקסטואליים: ציטוט ומפריד מקטע.
2. **בנייה.** השקף נכתב ב-HTML/CSS חופשי (11.5), עם tokens של התבנית.
3. **הסתכלות.** אחרי כל שקף ה-Agent חייב לקרוא ל-`slide_render` ולראות את התוצאה. אסור לסיים שקף "על עיוור".
4. **ביקורת עצמית** מול רשימת הבדיקה למטה, ותיקון.
5. **מבט על.** בסוף בניית מצגת ה-Agent קורא ל-`deck_render_contact_sheet` ובודק עקביות, גיוון ורצף.

**רשימת הבדיקה לכל שקף**

- האם יש נקודת מיקוד אחת ברורה, ורואים אותה ראשונה?
- האם התוכן ממלא את השקף, בלי אזור מת ובלי צפיפות יתר?
- האם ההיררכיה נקראת בשנייה אחת: כותרת, עיקר, פרטים?
- האם יש אלמנט חזותי שנושא את המסר, ולא רק טקסט?
- האם הטקסט קצר מספיק לקריאה מרחוק?
- האם השקף נראה שייך לאותה מצגת כמו שכניו, ועדיין שונה מהם?
- האם הכיוון, היישור והמרווחים עקביים?

ארבעה עקרונות:

1. **ה-API מוגדר באפליקציה.** ה-`ToolRegistry` הוא ה-Deck API: סט פונקציות מתועד מעל ה-CommandBus, שאינו יודע דבר על MCP או על harness מסוים. זה הלב; כל השאר הוא תעבורה.
2. **MCP הוא מתאם תעבורה דק, לא שכבת תכנון.** Claude Code CLI הוא תהליך נפרד, ואין לו דרך לקרוא לפונקציה בתוך האפליקציה. MCP הוא המנגנון היחיד שבו CLI כזה מקבל כלים מותאמים, ולכן יש מתאם שמעביר קריאות MCP אל ה-Deck API. ראה 11.4.
3. **ה-API מבוצע ב-webview.** מצב המסמך וה-renderer חיים שם. ה-Rust רק מעביר את הקריאה ומחזיר את התוצאה.
4. **ה-Agent לא נוגע בקבצים.** הוא רואה ומשנה את המצגת רק דרך ה-Deck API, שעובר דרך ה-CommandBus.

### 11.2 שכבת ה-Harness

<div dir="ltr">

```rust
#[async_trait]
pub trait AgentHarness: Send + Sync {
    fn descriptor(&self) -> HarnessDescriptor;        // id, name, capabilities, models
    async fn probe(&self) -> HarnessStatus;           // installed? version? logged in?
    async fn start(&self, cfg: SessionConfig, sink: EventSink)
        -> Result<Box<dyn AgentSession>>;
}

#[async_trait]
pub trait AgentSession: Send {
    async fn send(&mut self, turn: UserTurn) -> Result<()>;   // text + attachments + context
    async fn interrupt(&mut self) -> Result<()>;
    async fn close(self: Box<Self>) -> Result<()>;
    fn native_session_id(&self) -> Option<String>;            // for resume
}

pub struct SessionConfig {
    pub scope: Scope,                  // Deck | Slide(id) | Object(slide_id, element_ids) | Import(file)
    pub system_prompt: String,         // assembled from modules (11.6)
    pub mcp: McpEndpoint,              // url + bearer token, scoped to this session
    pub allowed_tools: Vec<String>,
    pub model: Option<String>,
    pub effort: Option<String>,
    pub resume: Option<String>,
    pub workdir: PathBuf,              // per-deck agent workspace
}

pub enum AgentEvent {
    SessionStarted { native_session_id: String, model: String },
    TextDelta { text: String },
    ThinkingDelta { text: String },
    ToolCallStarted { id: String, name: String, input: Value },
    ToolCallFinished { id: String, ok: bool, summary: String },
    TurnCompleted { usage: Usage, cost_usd: Option<f64>, duration_ms: u64 },
    Error { kind: ErrorKind, message: String, recoverable: bool },
    Exited { code: Option<i32> },
}

### 11.3 מתאם Claude Code CLI

התהליך מופעל מ-Rust כתהליך ארוך-חיים לכל סשן, עם זרימת JSON דו-כיוונית:

<div dir="ltr">

```
claude -p
  --input-format stream-json --output-format stream-json
  --verbose --include-partial-messages
  --restricted --disable-slash-commands
  --strict-mcp-config --mcp-config <session>/mcp.json
  --tools "Read,Grep,WebSearch,WebFetch"
  --allowedTools Read Grep WebSearch WebFetch "mcp__slidr__*"
  --permission-mode dontAsk
  --system-prompt-file <session>/system.md
  --model <model> [--effort <level>] [--resume <native-session-id>]

cwd = <session>/attachments      # --restricted confines Read and Grep to the working directory
env = no CLAUDE* / ANTHROPIC* variables;  Windows: CREATE_NO_WINDOW
```

`<session>/mcp.json`:

{ "mcpServers": { "slidr": {
    "type": "http",
    "url": "http://127.0.0.1:<port>/mcp/<sessionKey>",
    "headers": { "Authorization": "Bearer <token>" } } } }
```

</div>

- **אימות:** התהליך משתמש בהתחברות הקיימת של Claude Code במחשב. אין מפתח API באפליקציה.
- **תיקיית עבודה:** תיקיית `attachments/` של הסשן, בתוך תיקייה ייעודית לכל מצגת ב-app data. `--restricted` סוגר את כלי הקבצים לתיקיית העבודה, ולכן היא מכילה רק את מה שה-Agent רשאי לקרוא; `mcp.json` ו-`system.md` יושבים מעליה. כלל הרשאה עם נתיב (`Read(./attachments/**)`) אינו מגביל, רק מוסיף.
- **מיפוי אירועים:** `system/init` (הראשון בלבד; הוא חוזר בכל תור) → `SessionStarted`; `stream_event` (text_delta) → `TextDelta`; בלוקי `tool_use` / `tool_result` → `ToolCall*`; `result` → `TurnCompleted` עם `usage`. `total_cost_usd` מצטבר לסשן, ולכן העלות לתור היא הפרש. המיפוי המלא ב-ADR-001.

**ארבע הנקודות שלא היו מתועדות נבדקו ב-WG0-S1 (ADR-001):**

| נושא | מה נמצא |
|---|---|
| מבנה הודעת משתמש ב-stdin | `{"type":"user","message":{"role":"user","content":[...]}}`, כולל בלוקי `image` |
| עצירת תור באמצע | `{"type":"control_request","request_id":"…","request":{"subtype":"interrupt"}}` ב-stdin; התהליך נשאר חי. גיבוי שנבדק: הריגת התהליך ו-`--resume` |
| בידוד מהגדרות המשתמש | `--restricted --strict-mcp-config --disable-slash-commands`. לא `--safe-mode` (מבטל גם את שרת ה-MCP שלנו) ולא `--bare` (לא קורא את התחברות המנוי) |
| חסימת כלים מובנים | `--tools` קובע רשימה מדויקת |

**מתאם חלופי — Claude Agent SDK:** לא נדרש (ADR-001). נשאר אפשרות עתידית כמימוש נוסף של `AgentHarness`.

**מגבלת מדיניות:** Anthropic אינה מתירה למוצרי צד שלישי להציע התחברות עם מנוי claude.ai. לשימוש אישי במחשב שבו Claude Code מותקן זה לא רלוונטי, אבל אם Slidr יופץ כמוצר, יידרש מעבר למפתח API. הארכיטקטורה תומכת בזה (הגדרת סביבה למתאם), ואין צורך בשינוי קוד.

### 11.5 נתיב היצירה ב-HTML

מודלי שפה מעצבים הכי טוב ב-HTML/CSS. לכן נתיב היצירה הראשי של שקף חדש הוא `slide_create_from_html`: ה-Agent כותב שקף כ-HTML/CSS ב-1920×1080, והאפליקציה ממירה אותו לאובייקטים **באותו מנוע המרה של ייבוא HTML** (פרק 13). מנוע אחד משרת גם את הייבוא וגם את ה-AI.

**אין הגבלה על מה שה-Agent כותב.** כל HTML/CSS תקף מתקבל, והתוצאה נראית בדיוק כמו שנכתבה (עקרון הנאמנות, 5.9). מה שהמודל יודע לייצג הופך לאובייקטים עם ידיות עריכה; מאפיין CSS שאין לו שדה עובר לשדה `css` של האובייקט; תת-עץ שלא ניתן לפרק נשאר אובייקט `html`. ה-Agent לא צריך לדעת מה "נתמך".

יש רק **מוסכמות מומלצות**, שמשפרות את העריכוּת ולא את המראה:

- מיכל שורש 1920×1080. מותר כל layout: flex, grid, מיקום מוחלט (המנוע מודד את התוצאה המרונדרת).
- צבעים וגופנים דרך משתני ה-Theme: `var(--color-primary)`, `var(--font-heading)`. כך החלפת תבנית משפיעה על השקף, וערכים זהים ל-tokens מקושרים אליהם בהמרה.
- תמונות: `<img data-asset="<id>">` לנכס קיים, או `<img data-image-prompt="...">` שיוצר placeholder עם ה-prompt, למימוש מאוחר יותר.
- אייקונים: `<i data-icon="lucide:rocket">`. גרפים: `<div data-chart='{...}'>` הופך לאובייקט גרף שניתן לעריכה (גרף שצויר בדרך אחרת נשאר `html`).
- `data-name` ו-`data-role` נותנים שם ותפקיד לאובייקט; `data-anim` רומז על אנימציית כניסה.
- `data-keep-html` על אלמנט מורה למנוע לא לפרק אותו, גם אם אפשר.

תשובת הכלי כוללת: מזהי האובייקטים שנוצרו, שיעור העריכוּת (איזה חלק מהתוכן הפך לאובייקטים רגילים ומה נשאר `html`), ממצאי lint, וצילום השקף. כך ה-Agent מתקן את עצמו בלי התערבות.

עריכות נקודתיות נעשות ב-`element_update` ולא ביצירה מחדש, כדי לשמור על מזהים, אנימציות ועריכות ידניות של המשתמש.

### 11.6 הרכבת ה-prompt וההקשר

ה-system prompt מורכב ממודולים קבועים, זהים לכל harness. במתאם Claude Code הוא **מחליף** את ה-prompt המובנה של ה-CLI ואינו מתווסף אליו (ADR-001). Claude Code שומר את ה-system prompt של הבקשה הראשונה ומשתמש בו גם אחרי resume (`--system-prompt-snapshot`, ADR-010), ולכן שינוי במודולים לא מגיע לשיחה שחודשה; מה שמשתנה בין תורות עובר בבלוק ההקשר:

1. **תפקיד וכללי עבודה:** מעצב מצגות; לקרוא לפני שכותבים; לשנות את המינימום הנדרש; לא ליצור מחדש שקף כשאפשר לעדכן.
2. **הנחיות העיצוב** (9.1) במלואן.
3. **מדריך הכלים** ומוסכמות ה-HTML המומלצות (11.5).
4. **מודול היקף:** מה מותר ומה מצופה בסשן מצגת / שקף / אובייקט.
5. **שפה:** לענות בשפת המשתמש; תוכן השקפים בשפת המצגת.

בכל תור מוזרק בלוק הקשר עדכני:

<div dir="ltr">

```
<slidr_context>
scope: slide
deck: { title: "...", lang: "he", dir: "rtl", slides: 14, theme: "Midnight" }
current_slide: { id: "s_07", index: 7, name: "מפת דרכים" }
selection: [ { id: "e_31", type: "image", name: "hero-image" } ]
changed_since_last_turn: { slides: ["s_03"], elements: ["e_12", "e_31"] }
</slidr_context>
```

</div>

`changed_since_last_turn` (CMD-08) מונע מה-Agent לעבוד על מידע ישן אחרי שהמשתמש ערך ידנית.

## 13. ייבוא HTML (מונחה-Agent)

**כל קובץ HTML נתמך** (D6, D14, D17). את הייבוא מוביל ה-Agent (Claude Code CLI, דרך שכבת ה-harness), ולא אלגוריתם קבוע.

**למה Agent ולא פתרון דטרמיניסטי.** למצגות HTML אין מבנה אחיד: יש קבצים ארוזים שנפרקים בזמן ריצה, יש מצגות שנבנות ב-JS, יש עשרות דרכים לסמן שקף, להציג אותו ולנווט ביניהם. כל רשימה של פורמטים מוכרים וכללי זיהוי תכסה את הדוגמאות שראינו ותיכשל בקובץ הבא. Agent מסתכל על הקובץ שלפניו, מבין איך הוא בנוי, ומתאים את עצמו. לכן **אין באפליקציה שום ידע על פורמטים**: לא מתאמים, לא רשימת מבנים מוכרים, לא כללי זיהוי שקפים.

ההבטחה נשארת על המראה (5.9): השקף המיובא נראה כמו המקור, תמיד. מה שמשתנה מקובץ לקובץ הוא **שיעור העריכוּת** — כמה מהתוכן הפך לאובייקטים רגילים עם ידיות, וכמה נשאר אובייקטי `html`.

### 13.1 חלוקת העבודה

| מי | מה |
|---|---|
| **ה-Agent** | מבין את מבנה הקובץ: איפה השקפים, איך מציגים כל אחד, מה גודל העיצוב. מחליט מה נחשב שקף. מזהה Theme, שמות שקפים, הערות דובר ומעברים. שופט את התוצאה מול המקור ומתקן. משפר עריכוּת היכן שכדאי |
| **האפליקציה** | מריצה את הקובץ בסביבה מבודדת. מבצעת את מה שה-Agent מבקש: הרצת JS, צילום, לכידה. מודדת תת-עץ שנלכד וממירה אותו לאובייקטים (אותו מנוע של 11.5). מפעילה את שומר הנאמנות |

החלק הדטרמיניסטי היחיד הוא המדידה: בהינתן אלמנט מרונדר, לקרוא את המיקום והסגנון שלו מהדפדפן ולבנות ממנו אובייקטים. זה אותו מנוע שמשרת את `slide_create_from_html`, והוא לא יודע דבר על מבנה של מצגות.

### 13.2 כלי הייבוא

חלק מה-Deck API, זמינים רק בסשן ייבוא:

| כלי | תיאור |
|---|---|
| `import_inspect` | מתווה ה-DOM החי של הדף: עץ מקוצר עם תגית, id, class, מידות ומספר ילדים; רשימת stylesheets, משתני CSS וגופנים; גודל החלון |
| `import_eval` | הרצת JavaScript בתוך הדף המבודד והחזרת התוצאה. משמש לחקירה (שאילתות DOM, קריאת סגנונות) ולניווט (מעבר שקף ב-runtime של המצגת, שינוי תצוגה, המתנה לטעינה) |
| `import_screenshot` | צילום של חלון הדף או של אלמנט מסוים |
| `import_capture` | לכידת אלמנטים כשקפים, כמה בקריאה אחת. לכל שקף: קוד `before` שמביא אותו למצב הסופי, ואז האפליקציה אוספת את תת-העץ שה-Agent הצביע עליו, עם הסגנונות שחלים עליו, התמונות והגופנים, מעבירה למנוע ההמרה, ומחזירה מזהה שקף, שיעור עריכוּת, ותוצאת שומר הנאמנות (ADR-005) |
| `import_set_viewport` | שינוי גודל הדף המבודד, בדרך כלל לגודל העיצוב של המצגת, כדי שהבמה תוצג ב-100%. השוואה מדויקת מול המקור אפשרית רק ב-100% |
| קריאת המקור | Read ו-Grep של ה-harness על הקובץ בתיקיית הסשן, למשל כדי לגלות שהתוכן ארוז בתוך מחרוזת JSON |

בנוסף עומדים לרשות ה-Agent כל כלי המצגת הרגילים: `slide_update` (שם, הערות, מעבר), `theme_update`, `element_update`, `element_convert`, `slide_render`.

**למה `import_capture` ולא כתיבה מחדש של כל שקף.** שקף הוא אלפי tokens של HTML. מצגת של 35 שקפים שה-Agent מקליד מחדש תהיה איטית, יקרה ומועדת לטעויות העתקה. לכן ה-Agent **מצביע** והאפליקציה **מעתיקה**. ה-Agent כותב HTML בעצמו רק כשהוא בוחר לבנות משהו מחדש, למשל כדי להפוך אזור לעריך יותר.

### 13.5 סט הבדיקה

הייבוא נבדק על **מגוון** קבצים, לא על קובץ אחד. `examples/E-CIX NG - standalone.html` הוא דוגמה אחת בסט, ואין באפליקציה שום טיפול ייחודי בו.

הסט כולל לפחות 8 קבצים ממקורות שונים, שמכסים:

| סוג | מה הוא בודק |
|---|---|
| מצגת פשוטה שנכתבה ביד: אלמנט לכל שקף, CSS ב-`style` | המקרה הקל; עריכוּת קרובה ל-100% |
| מצגת שנוצרה ב-AI עם classes ו-stylesheet משותף | איסוף הסגנונות שחלים על תת-עץ |
| קובץ ארוז שנפרק בזמן ריצה ונבנה ב-JS (קובץ הדוגמה) | הרצת scripts, חקירת DOM חי, Shadow DOM |
| reveal.js | runtime שמציג שקף אחד בכל פעם; שקפים אנכיים ו-fragments |
| ייצוא של Marp או Slidev | מבנה שנוצר על ידי כלי |
| מצגת עם canvas, גרפים של ספרייה חיצונית או אנימציות CSS | תוכן שנשאר `html` ועדיין נראה ומתנגן נכון |
| עמוד אחד ארוך שנגלל, בלי חלוקה לשקפים | שיקול דעת: ה-Agent מציע חלוקה ומבקש אישור |
| מצגת באנגלית (LTR) עתירת תמונות | כיוון, תמונות, נכסים |

**קריטריוני המעבר (IMP-10):**

1. מספר השקפים והסדר נכונים בכל קובץ.
2. כל שקף נראה כמו המקור (שומר הנאמנות עובר על כולם).
3. שיעור עריכוּת חציוני של 80% לפחות; בקבצים הפשוטים 95% לפחות.
4. כל הטקסט ניתן לעריכה, כאובייקט `text` או בתוך אובייקט `html`.
5. גופנים מוטמעים נשמרים ומוצגים בלי התקנה.
6. לפחות 7 מתוך 8 הקבצים מיובאים בלי התערבות המשתמש מעבר לאישור התוכנית.
7. ייצוא המצגת המיובאת חזרה ל-HTML נראה כמו המקור.
8. לכל קובץ נרשמים זמן הייבוא והצריכה, כבסיס למעקב.

### 14.5 אסטרטגיית בדיקות

- **הערכת AI:** סט של 10 בקשות קבועות ("מצגת משקיעים של 8 שקפים...") שרץ ידנית לפני כל גרסה, עם ציון lint אוטומטי והערכה חזותית.
