# ADR-007 — חוזה המודל, ה-commands וההיסטוריה

סטטוס: **הוכרע** · 2026-10-03 · משימות: WG1-T01 עד T12 · קוד: `packages/model/`, `apps/desktop/src/document/`, `apps/desktop/src-tauri/src/storage/`

זה החוזה ש-PLAN סעיף 3 קובע שנסגר בתחילת M1: סכמת המודל ורשימת ה-commands. WG2–WG11 נשענים עליו. שינוי בו אחרי הסגירה מעדכן את המסמך הזה.

## ההחלטה

1. **הסכמה** היא סכמות ה-Zod שב-`packages/model/src/schema/`, כפי שמתוארות ב-SPEC 5.2–5.7, עם ארבעה הבדלים שנכתבו בחזרה ל-SPEC 5.3 (ראה למטה). טיפוסי TypeScript נגזרים מהן ב-`z.infer`, ו-JSON Schema ב-`toJsonSchema()` (T02).
2. **19 commands** הם הדרך היחידה לשנות מצגת. ה-UI וה-Agent משתמשים באותם commands.
3. **ההיסטוריה** בנויה על patches של Immer. transaction הוא מזהה (`txId`) ולא אובייקט שנפתח ונסגר.
4. **אין קיצורי דרך:** ה-store של המצגת נגזר מה-bus ואין לו פונקציית כתיבה.

## קטלוג ה-commands

כל command הוא אובייקט JSON שטוח עם שדה `type`. הקטלוג הוא `commandDefs` ב-`commands/index.ts`, והאיחוד של כולם הוא הסכמה `Command`.

| command | מה הוא עושה | כללים |
|---|---|---|
| `deck.setMeta` | כותרת, שפה, כיוון, סגנון תמונות | |
| `theme.update` | שינוי tokens | `colors`, `fonts` ו-`textStyles` מתמזגים מפתח אחר מפתח; השאר מוחלפים |
| `theme.replace` | החלפת ה-Theme כולו | להחלפת תבנית |
| `layout.add` / `layout.update` / `layout.remove` | ניהול layouts | הסרת layout מנתקת ממנו את השקפים, והתוכן שלהם נשאר |
| `asset.add` | רישום נכס שכבר נשמר בדיסק | אותו נכס פעמיים לא משנה דבר |
| `slide.add` | שקף שלם (JSON), במיקום | מזהי האובייקטים ייחודיים בכל המצגת; ציר האנימציות מפנה רק לאובייקטים של השקף; `layoutId` קיים |
| `slide.remove` | הסרת שקף אחד או יותר | |
| `slide.move` | העברת שקפים למיקום | המיקום נספר ברשימה בלי השקפים שזזים; הם שומרים על הסדר שהיה להם |
| `slide.update` | שם, layout, רקע, הערות, מעבר, הסתרה, `css` | |
| `slide.setTimeline` | החלפת ציר האנימציות של שקף | מזהי צעדים ייחודיים; כל צעד מפנה לאובייקט שקיים בשקף |
| `element.add` | אובייקט שלם, בשקף או בתוך קבוצה, במיקום בסדר השכבות | |
| `element.remove` | הסרת אובייקטים בכל עומק | נמחקים גם צעדי האנימציה שלהם, וקבוצה שנשארה ריקה |
| `element.update` | עדכון שדות של אובייקט | ראה "patch" למטה |
| `element.reorder` | סדר שכבות: `front`, `back`, `forward`, `backward` או מיקום | כל האובייקטים באותו הורה |
| `element.group` | קיבוץ, במיקום של העליון שבהם | מזהים ואנימציות נשמרים; מסגרת הקבוצה היא המלבן החוסם, כולל סיבוב |
| `element.ungroup` | פירוק במקום | הסיבוב, השיקוף, השקיפות, הנעילה וההסתרה של הקבוצה עוברים לילדים; האפקטים, הקישור וה-`css` של הקבוצה נזרקים, וכך גם צעדי האנימציה שלה |
| `text.set` | RichText של תיבת טקסט, צורה או תא בטבלה | `cell` נדרש לטבלה ורק לה |

**patch.** ב-`element.update`, ב-`slide.update`, ב-`layout.update` וב-`deck.setMeta` כל מפתח ב-patch מחליף את השדה כולו, ו-`null` מוחק שדה אופציונלי. אין מיזוג עמוק. התוצאה של `element.update` מאומתת מול הסכמה של סוג האובייקט, ו-`id`, `type` ו-`children` אינם ניתנים לשינוי בו. ב-TypeScript יש `updateElement()` עם patch מוקלד לפי סוג.

**שגיאות.** command שנדחה זורק `CommandError` עם `code` מתוך: `unknown_command`, `invalid_payload`, `not_found`, `conflict`, `invalid_state`, והמצגת לא משתנה. ההודעות כתובות כך שה-Agent יבין מהן מה לתקן; אובייקט שנמחק מחזיר "may have been deleted" (CMD-07).

**מה לא נכנס לקטלוג, ולמה.** שכפול שקף, העתקה והדבקה, יישור ופיזור, והחלת תבנית הם פונקציות שמחשבות commands מהקטלוג (`slide.add` עם מזהים חדשים, רצף של `element.update`, וכו'). ההיסטוריה נשענת על patches, ולכן כל command מקבל undo בלי קוד ייעודי; אין סיבה להגדיל את החוזה בשביל פעולה שאפשר להרכיב. קיבוץ ופירוק כן נכנסו: הרכבה שלהם מהסרה והוספה הייתה מוחקת את צעדי האנימציה של האובייקטים.

## היסטוריה ו-transactions

`CommandBus.dispatch(command, { actor, txId, label })`, כמו בתרשים של SPEC פרק 6.

- **צעד undo.** כל dispatch בלי `txId` הוא צעד. dispatch עם `txId` מתמזג לצעד העליון אם יש לו אותו `txId` ואותו `actor`. כך גרירה, רצף הקלדה (ADR-006 כלל 3) ותור שלם של Agent הם צעד אחד: הקורא מחליט מתי מתחיל צעד חדש בכך שהוא לוקח מזהה חדש.
- **שזירה.** אם המשתמש עורך בזמן שה-Agent עובד (CMD-07), הצעדים נרשמים לפי סדר הזמן: חלק מהתור, עריכת המשתמש, ההמשך של התור. ההיסטוריה נשארת לינארית, וה-patches ההפוכים תמיד מופעלים בסדר הנכון. המחיר: תור שהמשתמש עבד באמצעו הוא יותר מצעד undo אחד ב-Ctrl+Z.
- **ביטול תור AI (CMD-06).** `transactionInfo(txId)` מחזיר כמה צעדים יבוטלו ו-`otherEdits`, מספר העריכות שאינן של התור; זה ה-N של האזהרה. `undoTransaction(txId)` מבטל עד לפני הצעד הראשון של התור, והכול עובר ל-redo.
- **ביטול באמצע.** `rollback(txId)` מבטל transaction שהוא השינוי האחרון בלי להשאיר redo (Esc בזמן גרירה).
- **אצווה אטומית.** `batch(commands)` מחיל הכול או כלום, בצעד אחד. זה הבסיס של `deck_apply_ops`.
- **actor** (CMD-04) הוא מחרוזת: `user` או `agent:<sessionId>:<turnId>`. undo ו-redo נרשמים כפעולה של המשתמש.
- **מגבלה:** 200 צעדים. אין חותמת `updatedAt` בכל command (היא הייתה נכנסת להיסטוריה); הזמן נחתם בשמירה.
- **NFR-03:** על מצגת של 200 שקפים ו-6,000 אובייקטים נמדדו כ-0.02ms ל-undo או redo, 0.12ms ל-`element.update` ו-0.45ms ל-`element.add` (שסורק את כל מזהי המצגת). הבדיקה האוטומטית דורשת פחות מ-16ms.

## מה שסביב ה-bus

- **מנויים.** כל שינוי מודיע `ChangeEvent`: סוג (`apply`, `undo`, `redo`, `rollback`, `reset`), המצגת לפני ואחרי, ה-patches, ומה הושפע (`affected`: שקפים, אובייקטים, layouts, נכסים, Theme, סדר השקפים). שמירה אוטומטית, lint, תמונות ממוזערות ותקציר השינויים נשענים עליו. מנוי שזורק לא נראה כמו command שנכשל.
- **`DeckStore`** (Zustand, בלי React): `deck`, `canUndo`, `canRedo`, `revision`. אין לו `setState`.
- **`SelectionStore`** (CMD-05): השקף הנוכחי, שקפים ואובייקטים נבחרים, האובייקט שבעריכת טקסט. לא חלק מהמסמך ולא מה-undo. כשמחיקה, undo או עריכה של ה-Agent מסירים משהו נבחר, הבחירה מצטמצמת למה שקיים; כשהשקף הנוכחי נמחק, עוברים לשקף שתפס את מקומו.
- **`ChangeDigest`** (CMD-08): לכל סשן של Agent, השקפים והאובייקטים ששינו אחרים מאז התור הקודם שלו, ומה מהם כבר לא קיים. undo של המשתמש על עבודת ה-Agent נחשב שינוי שה-Agent צריך לשמוע עליו.
- **מזהים.** מצגת: ULID. שקפים, אובייקטים, צעדים ו-transactions: קידומת ושמונה תווים (`e_k3x9a2bq`), קצרים כדי שה-Agent יעתיק אותם בלי טעויות. מזהי אובייקטים ייחודיים בכל המצגת, כך שאפשר למצוא אובייקט לפי מזהה בלבד.
- **סיבוב ושיקוף.** השיקוף קורה בתוך התיבה של האובייקט, לפני הסיבוב (כמו `rotate() scale(-1, 1)` ב-CSS). הפירוק של קבוצה נשען על הסדר הזה.

## טעינה, הגירות ושמירה

- `loadDeck(raw)` מאמת `deck.json`, ומריץ קודם הגירות לפי `schemaVersion` (T10). קובץ מגרסה חדשה יותר, קובץ שאינו מצגת וקובץ פגום נדחים עם `DeckLoadError` וקוד. כשהייתה הגירה, השירות שפותח את הקובץ שומר קודם עותק של המקור (DOC-04).
- `prepareForSave(deck)` מחזיר את מה שנכתב לקובץ: עם זמן שמירה, ובלי נכסים שאיש לא משתמש בהם. המצגת בזיכרון שומרת אותם, כדי ש-undo אחרי שמירה יעבוד (SPEC 5.7).
- **מתי נכס בשימוש.** כשהמזהה שלו מופיע במקום כלשהו במצגת מחוץ לטבלת הנכסים: בשדה של המודל, אבל גם בתוך ה-markup של אובייקט `html` או בשדה `css`, שהמודל לא מפענח. זה חיפוש מחרוזת על ה-JSON, לא מעבר על השדות, ולכן הוא לא יכול לפספס הפניה שעוד לא הוגדרה בקוד (D14). גופנים משמשים לפי שם המשפחה ולא לפי מזהה, ולכן לא נמחקים לעולם בשמירה.

## אחסון: הצד של Rust (T07–T09, T11)

קוד: `apps/desktop/src-tauri/src/storage/`, `assets/`, `commands.rs`. בצד ה-webview: `apps/desktop/src/document/` (`DocumentService` והמתאם `tauriStorage`).

- **Rust לא מפענח את המצגת.** הוא מקבל ומחזיר את `deck.json` כטקסט, וקורא ממנו רק `schemaVersion` ואת שמות הקבצים בטבלת הנכסים. האימות, ההגירה והניקוי של נכסים קורים ב-webview (`loadDeck`, `prepareForSave`).
- **workspace** לכל מצגת פתוחה ב-`%APPDATA%\dev.slidr.app\workspaces\<id>\`, באותו מבנה כמו קובץ `.slidr` (SPEC 5.8), ועוד `.workspace.json` (נתיב המקור, האם יש שינויים שלא נשמרו, זמני שמירה) ו-`.lock`, ששניהם לא נארזים.
- **12 פקודות IPC:** `storage_new`, `storage_open`, `storage_write_deck` (שמירה אוטומטית), `storage_save`, `storage_close`, `storage_list_recoverable`, `storage_recover`, `storage_backup`, `asset_import_file`, `asset_import_bytes`, `recents_list`, `recents_remove`. שגיאות מגיעות כ-`{ kind, message }`, עם `kind` מתוך סט סגור. כל עבודת קבצים רצה מחוץ ל-main thread.
- **שמירה אטומית (DOC-01):** הקובץ נכתב לקובץ זמני באותה תיקייה, עובר sync, ואז rename על היעד. כשל בכל שלב משאיר את הקובץ הקודם שלם. ה-workspace מסומן "לא נשמר" לפני האריזה, והסימון יורד רק אחרי שהקובץ החדש במקומו.
- **שחזור אחרי קריסה (DOC-03):** `DocumentService` כותב את ה-workspace כ-3 שניות אחרי השינוי האחרון. כל workspace פתוח מחזיק נעילה של מערכת ההפעלה על קובץ `.lock` שלו. "נשאר מקריסה" פירושו שאף מופע רץ של האפליקציה לא מחזיק אותו. כך מופע שני לא מוחק workspace של מופע ראשון.
- **נכסים (T09):** המזהה הוא sha256 של התוכן, ותוכן זהה לא נכתב פעמיים. הסוג נקבע לפי התוכן ואחר כך לפי הסיומת, ומידות התמונה נקראות מהכותרת בלבד. הדבקה וגרירה עוברות כגוף IPC גולמי ולא כמערך מספרים ב-JSON. הנכסים מוצגים דרך ה-asset protocol של Tauri, שמוגבל לתיקיית ה-workspaces.
- **שמירה עם נכס חסר** לא נכשלת: הנכס לא נארז, והוא מופיע ב-`missingAssets` שבתשובה.
- **נבדק באפליקציה עצמה** (`pnpm tauri dev`, בדיקת עשן זמנית שהוסרה):
  - ייבוא נכס בגוף גולמי, עם שם קובץ עברי;
  - טעינת הנכס דרך ה-asset protocol;
  - שמירה אוטומטית, שמירה, ופתיחה שמחזירה את אותו תוכן;
  - קבצים אחרונים, ושגיאת `not_found`.

  חוץ מזה יש 35 בדיקות ב-Rust ו-11 בדיקות של `DocumentService` מול אחסון מדומה.
- **ל-WG13-T04 (CSP):** כשה-CSP יוקשח, צריך להתיר `asset: http://asset.localhost` ב-img-src, media-src ו-font-src, ו-`ipc: http://ipc.localhost` ב-connect-src.
- **לא נעשה:**
  - הגבלת גודל נגד zip bomb;
  - סיבוב EXIF במידות של JPEG;
  - ניקוי SVG (שייך ל-SEC-06, למי שמרנדר);
  - ניסיון חוזר כש-Windows מסרב ל-rename כי תוכנה אחרת מחזיקה את קובץ היעד פתוח;
  - שיוך סיומת (DOC-06, P2).
- **ל-WG3:** אחרי רענון של ה-webview בפיתוח, ה-workspace עדיין רשום כפתוח ב-Rust. לכן הוא לא יוצע לשחזור, וצריך לשמור את המזהה שלו ב-`sessionStorage` ולקרוא ל-`recover` איתו. גם תפריט הקובץ ודיאלוגי הבחירה (`@tauri-apps/plugin-dialog`, ההרשאות כבר קיימות) מתחברים ל-`DocumentService` ב-WG3-T02.

## חלופות שנבחנו

- **JSON Merge Patch (מיזוג עמוק) ב-`element.update`.** נוח ל-`{ frame: { x } }`, אבל שובר ערכים שהם איחוד: patch של `{ fill: { kind: 'solid', … } }` על gradient משאיר את `stops`, ו-`{ color: { value } }` על `{ token }` משאיר את שניהם. החלפת שדה שלם צפויה תמיד, ו-Deck API (WG10-T05) יכול להציע ל-Agent נוחות משלו מעליה.
- **היסטוריה של תמונות מצב** במקום patches. עם Immer זה זול באותה מידה ופשוט יותר, אבל SPEC (CMD-02) ו-PLAN (T04) קבעו patches, וה-patches הם גם מה שמנויים כמו התמונות הממוזערות צריכים.
- **transaction עם begin/commit.** מזהה שהקורא בוחר עושה את אותה עבודה בלי מצב פתוח שצריך לזכור לסגור.

## השלכות

- **WG2:** גרירה, שינוי גודל וסיבוב שולחים `element.update` עם `txId` אחד לכל מחווה, ו-`rollback` ב-Esc. אובייקט שלא נגעו בו שומר על זהות האובייקט שלו, כך ש-memo של React עובד.
- **WG4:** רצף הקלדה הוא `text.set` עם `txId` אחד; הפסקה או הזזת סמן לוקחות מזהה חדש (ADR-006).
- **WG10:** כל כלי כתיבה של ה-Deck API ממופה ל-commands; `deck_apply_ops` הוא `batch`; תור הוא `txId` אחד עם `agentActor(session, turn)` (T07); בלוק ההקשר לוקח את `changed_since_last_turn` מ-`ChangeDigest`. הגדרות הכלים נבנות מ-`toJsonSchema` (MCP-03).
- **WG3:** בונה על `DeckStore` ו-`SelectionStore`; קיצורי undo/redo קוראים ל-`bus.undo()` ו-`bus.redo()`.
