# ADR-108 — PowerPoint files in and out

Status: Implemented on 2026-10-20. It takes back one line of the README, "Out of scope: PowerPoint (`.pptx`) compatibility".

## Request

"הוסף במערכת תמיכה E2E ביבוא ויצוא מצגות pptx (powerpoint)": end-to-end import and export of PowerPoint presentations.

## Context

- A deck is an object model at 1920×1080. Most of it has a direct counterpart in PresentationML: text with runs and paragraphs, preset shapes, lines, pictures, tables, charts, video and audio, groups, notes, transitions and animations. Some of it has none: an `html` object, a slide's own CSS, a backdrop blur, an image filter or duotone, a conic gradient.
- The look of a deck comes from its theme. Colours are tokens (`primary`, `text`, …), and text takes its style from the theme's text styles. PowerPoint keeps the same idea in a theme part, a slide master and its layouts. Its text runs through a long chain of inheritance: the master's text styles, then the placeholder, then the shape's list style, then the paragraph and the run. Colours go through the master's colour map and transforms (`lumMod`, `tint`, `alpha`, …).
- The shapes, list markers, cell look and paragraph direction of a deck are computed in TypeScript (`@slidr/renderer`), and so is everything the export of HTML knows. The Rust side keeps files, assets and capture.
- New dependencies wait for approval (README). A `.pptx` is a ZIP of XML parts, and the browser's `CompressionStream` and `DecompressionStream` do the deflate.

## Decision

- **One package, `@slidr/pptx`, with no dependency but the model and the renderer.** It has its own ZIP reader and writer (ZIP64 when it reads), its own XML parser, which names each element by the standard prefix of its namespace (the strict schemas too), and an XML writer. The same code runs in the app, in a plain browser and in Node. `exportPptx(deck, options)` gives the bytes, the warnings, the fonts and the media that went in. `importPptx(bytes, options)` gives a deck the model's schemas accept, its warnings and its fonts.
- **What only the app can do is passed in as functions.** These are: an asset's bytes; a picture of an element PowerPoint cannot draw; a WebP or AVIF picture as PNG; a poster frame of a video; the counterpart of a font for another script ([ADR-105](ADR-105-fonts-of-every-language.md)); the prompt text of the placeholders, in the UI language; and, on import, where an asset is stored. In the app (`desktop/src/pptx/`), the picture is a native capture of the element twice, on black and on white, so its transparency comes through. In a plain browser it is an SVG `foreignObject` drawn on a canvas, with the deck's fonts embedded.
- **Units.** 1 px is 6,350 EMU and half a point, so the slide is 12,192,000 × 6,858,000 EMU, PowerPoint's own 16:9. A file of another size is scaled to fit and centred on import. Its layouts keep their own boxes, as PowerPoint shows them.
- **The theme becomes a theme, a master and layouts.** Tokens map to scheme colours: `bg`→`bg1`, `text`→`tx1`, `surface`→`bg2`, `muted`→`tx2`, `primary`→`accent1`, `secondary`→`accent2`, `accent`→`accent3`. A colour written as a token is written as a scheme colour, so a change of theme in PowerPoint recolours the deck. The heading and body fonts become `+mj` and `+mn`, with the counterparts as the East Asian and complex-script fonts. Each layout of the deck becomes a slide layout with its background, its drawings and its placeholders. A slide on no layout gets a "Title Only" layout, so PowerPoint still treats its title as the title. A placeholder of the slide is written as a placeholder of its role. On import the way back is the same, and a colour that is an untransformed scheme colour comes back as its token. A layout that draws nothing and offers no more than a title is not kept, so a round trip adds no layouts.
- **Text is written whole.** Every run carries its full properties in schema order, so a file reads the same in a program that does not walk the inheritance chain. Line height is an exact `spcPts` (CSS line height × the largest size in the paragraph); a percentage on import is read as ×1.2. Paragraph alignment is physical (`l`/`r`), computed from the direction, and `rtl` is set per paragraph. Lists use `buChar` and `buAutoNum`. An outline and a shadow of text (`-webkit-text-stroke`, `text-shadow`) become the run's `a:ln` and effects. The way back reads them as CSS text effects.
- **Outlines are moved to the edge.** Slidr strokes a closed shape inside its frame; PowerPoint strokes on the edge. Export insets the frame by half the width, and import grows it back.
- **What PowerPoint has no object for goes in as its picture, and is said.** This covers an `html` object, an image with a filter, a mask PowerPoint has no geometry for, or duotone. A repeating gradient becomes a pattern fill, and a conic one its nearest linear gradient. A slide's CSS and a blur are not kept. Each of these is a warning of its own, with the slides it is on.
- **Lines.** A straight line of two points is a connector. An elbow, a curved or a multi-point line is a freeform. LibreOffice reroutes connector geometry of its own accord, and a freeform reads the same everywhere. On import an open freeform becomes a line again, so its arrowheads come back.
- **Tables are written in screen order.** A right-to-left table is written with its columns reversed and no `rtl` attribute, because LibreOffice ignores it; the cells read the same either way. Each cell carries its own fill and borders under the "No Style, No Grid" table style. On import, a table style is read into explicit cells. The built-in styles python-pptx and PowerPoint name without writing (Medium Style 2 – Accent 1, Medium Style 2, Table Grid, No Style) are defined in the package.
- **Charts stay charts.** A chart is a `c:chartSpace` with its cached values and an embedded workbook, so it can be edited in PowerPoint. This covers bar, column, line, area, pie, doughnut, scatter and radar charts. The way back reads the same types, their series, categories, colours, title, legend, axes and labels. A type Slidr does not have is drawn as the nearest and said.
- **Motion.** A slide's transition maps to the nearest PowerPoint transition, and each click group of its timeline to `p:timing` with the presets (appear, fade, fly in, wipe, zoom, and emphasis). Media uses `p14:media` with its trim and a poster frame. An animation or transition that is only near is said, both ways.
- **Import reads the inheritance PowerPoint applies.** That is the master's text styles, the layout's and the slide's placeholders, the shape's `p:style` references (a fill, line and font colour of the theme), the colour map and the transforms. SmartArt comes in as the drawing part PowerPoint saved with it. An equation or OLE object comes in as its fallback picture. EMF, WMF and TIFF pictures, linked media and unknown objects are left out and said.
- **The file goes through the app's paths.** "Export to PowerPoint…" opens a dialog with the HTML export's choices (all slides or a range, with or without animations; hidden slides are left out), then the save dialog, and `write_export` now accepts `.pptx`. "Import PowerPoint…" and "Load from file" on the welcome screen read the file with a new command, `pptx_read`. It takes an absolute path to a `.pptx` file that is a file, up to 2 GiB. In a plain browser the file is a download and a chosen file. An import opens as a new document (`DocumentService.createFrom`): its assets are stored in the new workspace, nothing of the open document goes until the new one is ready, and the question about unsaved changes comes first.
- **A file that is not a presentation is told apart.** An OLE compound file is either a password-protected `.pptx` or the old `.ppt`, and the message says so. A file that is not a ZIP, or has no presentation part, is "not a PowerPoint presentation". A package that breaks while it is read is "damaged".

## Consequences

- A deck can go to PowerPoint, Keynote and Google Slides with its text, shapes, tables and charts editable. A deck made there can come back as a deck of objects, with its theme as the deck's theme and its layouts as the deck's layouts.
- **Fonts are not embedded.** PowerPoint shows a font only where it is installed. The export dialog says so and names the families. The import names the families this computer does not have, in the app; a browser cannot list installed fonts, so it names none.
- What goes in as a picture cannot be edited in PowerPoint. A scripted `html` object in a plain browser is drawn without its scripts' work; the native capture in the app draws it as it runs.
- A shape has no opacity of its own in PowerPoint, so an element's opacity goes into its colours. On the way back it is the alpha of the fill, not the element's opacity.
- The strings are in Hebrew and English and in the fourteen other UI languages.

## Checks

- Unit tests of `@slidr/pptx` (38) cover:
  - the ZIP container, the XML of the parts, relationship targets, SVG and DrawingML paths, and Office's own colour transforms (`2F5597` and `8FAADC` from `4472C4`);
  - export of text, shapes, pictures, lines, tables, charts and the pictures of what PowerPoint has no object for, of hidden slides and a range, and of layouts, notes, transitions and animations;
  - import of a fixture written by python-pptx (`src/fixtures/foreign.pptx`, made by `src/fixtures/make-fixture.py`): a title slide, bullets, styled shapes, a connector, a table, two charts, a cropped picture, a group, a background, notes and Hebrew;
  - round trips of the renderer's reference deck: its slides, texts and theme, the place and size of every object, a layout, transitions and animations, right to left, and a video with its poster and trim.
- Rust: `a_powerpoint_file_is_written_too`, and `a_powerpoint_file_is_read_and_nothing_else_is` (a relative path, another extension, a folder and a missing file are refused).
- End-to-end, `desktop/e2e/pptx.spec.ts` (5 tests), in Chromium against the dev server:
  - export from the File menu, with the file read back in Node: three slides of four, their texts, a transition and a timeline;
  - a range without animations;
  - import of the fixture: six slides, the title, a table, a chart, a picture, a group and a line, with the picture's asset stored;
  - a round trip through both menus: texts, frame and opacity;
  - a text file refused, with the open deck kept.
- Accessibility: `a11y-audit.spec.ts` now holds the PowerPoint export dialog, its report and the report of an import to no serious or critical fault, in Hebrew and English, light and dark.
- Visual: the reference and chart decks were exported and rendered by LibreOffice (`soffice --convert-to pdf`, then `pdftoppm`), and compared with Slidr's own renders. The fixture and three of LibreOffice's templates (Vivid, Beehive, Inspiration) were imported and compared with LibreOffice's renders of the same files. A round trip through the app's menus, with real pictures, was compared with the original. Each difference found was fixed: the rerouted connectors, "contain" pictures, the order of right-to-left table cells, stripes, outlined text, the colour of a shape's text from its style, a table style that is never written, outlines of a theme's shapes, and arrowheads.
- Not run: PowerPoint, Keynote and Google Slides themselves (this was a Linux container), the Tauri paths (`pptx_read`, the save and open dialogs, the native capture) on Windows, and the suites in Edge.
