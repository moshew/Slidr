# ADR-002 — מתאם התעבורה MCP: rmcp על HTTP מקומי, מפנה ל-webview

סטטוס: **הוכרע** · 2026-10-02 · spike: WG0-S2 · קוד: `spikes/s2-mcp-bridge/`

## ההחלטה

מתאם התעבורה (`src-tauri/mcp_bridge`) נבנה עם **rmcp** (Streamable HTTP) מעל axum, כפי שה-SPEC קובע. המתאם דק באמת: כ-100 שורות, בלי שום לוגיקה של כלים. הגדרות הכלים נרשמות מה-webview בעליית האפליקציה, וכל קריאה מועברת ל-webview וחוזרת.

נבדק מקצה לקצה: Claude Code 2.1.287 קרא לשלושה כלים דרך המתאם (אחד מחזיר טקסט, שניים מחזירים תמונה), קיבל טקסט בעברית בלי שיבוש, וקרא נכון את מילות הקוד מתוך שתי התמונות.

## מה נבדק

| דרישה | תוצאה |
|---|---|
| MCP-01: האזנה רק ל-127.0.0.1, פורט אקראי | עובד. rmcp בודק גם את כותרת `Host` (הגנה מ-DNS rebinding) כברירת מחדל |
| MCP-02: נתיב ו-token לכל סשן | `/mcp/<sessionKey>` + `Authorization: Bearer`. token שגוי או מפתח לא מוכר → 401. מפתח הסשן זמין בתוך `call_tool` |
| MCP-03: הגדרות הכלים מגיעות מ-TypeScript | ה-webview רושם שם, תיאור ו-JSON Schema ב-`invoke`; `list_tools` מחזיר את מה שנרשם. אין הגדרת כלי ב-Rust |
| MCP-04: העברה ל-webview וחזרה | אירוע Tauri ל-webview, תשובה ב-`invoke`, עם timeout של 60 שניות |
| MCP-06: החזרת תמונה | בלוק `image` (PNG ב-base64) מגיע למודל. המודל קרא `CANVAS-7391` ו-`DOM-5824` מהתמונות ואת הכותרת העברית |

התקורה של הגשר עצמו זניחה: פחות מ-2ms בתוך האפליקציה, וכ-11ms נוספים של HTTP ו-CLI. NFR-04 (פחות מ-50ms לקריאת כלי, לא כולל רינדור) מתקיים ברווח גדול.

**מחיר התלות:** rmcp ו-axum מוסיפים 49 crates (209 ← 258) וכ-5MB לקובץ ההרצה (8.3 ← 13.2MB, כולל גם tokio מלא ו-webview2-com).

## ממצאים

**1. מלכודת: "מחובר" עם אפס כלים.** Claude Code מדבר בגרסת הפרוטוקול `2026-07-28` (בלי סשן, `server/discover` במקום `initialize`). בגרסה הזו תוצאת `tools/list` חייבת לשאת `ttlMs` ו-`cacheScope`. rmcp משאיר אותם ריקים כברירת מחדל, וה-CLI דוחה את כל הרשימה בשקט: השרת מופיע כ-`connected`, רשימת הכלים ריקה, והמודל **המציא** קריאות כלים ותוצאות בטקסט. התיקון הוא שורה אחת (`.with_ttl_ms(0).with_cache_scope(Private)`), אבל הלקח רחב יותר:

- **המתאם מאמת בתחילת כל סשן ש-`init.tools` מכיל את כלי `mcp__slidr__*` הצפויים.** אם לא, התור נעצר עם `Error` ברור ולא ממשיך. מודל בלי כלים לא נכשל; הוא ממציא.
- בדיקת העשן של המתאם מול ה-CLI האמיתי (ADR-001) כוללת קריאת כלי אחת.

**2. גם שרת שנכתב ביד עובד.** שרת JSON-RPC של 25 שורות (`mini-mcp.mjs`: `initialize`, `tools/list`, `tools/call`, תשובות JSON רגילות, בלי SSE ובלי סשן) התחבר ל-CLI ושירת קריאת כלי. כלומר rmcp אינו הכרחי. הוא נבחר בכל זאת משיקול אחד: הפרוטוקול זז (ה-CLI כבר בגרסה חדשה מזו שה-SPEC נכתב מולה), ועדיף שהמעקב אחריו יהיה של ספרייה ולא שלנו. אם rmcp יפגר אחרי ה-CLI, שרת ידני של כ-150 שורות הוא תחליף מוכח, והחלפתו לא נוגעת ב-Deck API.

**3. ה-CLI מחכה לכלים.** חיבור ה-MCP אסינכרוני, אבל התור הראשון לא יוצא לפני שרשימת הכלים הגיעה (נבדק עם עיכוב של 4 שניות). אין צורך בהשהיה מצד האפליקציה.

**4. ה-CLI שומר תמונות לדיסק.** כל תמונה שחוזרת מכלי נשמרת כקובץ תחת `~/.claude/projects/<תיקיית הסשן>/`. סשן ארוך עם הרבה צילומי שקפים צובר שם קבצים. ניקוי התיקייה הזו כשמצגת נמחקת או כשסשן מתחדש נכנס ל-WG10-T11.

**5. מגבלות גודל וזמן שצריך להכיר.** rmcp מגביל גוף בקשה ל-4MB כברירת מחדל: רלוונטי לקלט של כלי (למשל HTML גדול עם תמונות מוטמעות ב-`slide_create_from_html`), לא לפלט. צד ה-CLI מגביל קריאת כלי ל-60 שניות; לכלי תמונות (MCP-04) צריך להאריך דרך משתנה סביבה לתהליך. ייבדק ב-WG12-T04, כשיהיה כלי איטי אמיתי.
